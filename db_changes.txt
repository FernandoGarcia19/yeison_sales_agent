DB SCHEMA CHANGES — yeison_sales_agent
=======================================
Apply these directly against yeison_db (no Alembic).

----------------------------------------------------------------------
1. Add conversation_id to lead table
----------------------------------------------------------------------
ALTER TABLE public.lead
    ADD COLUMN conversation_id BIGINT REFERENCES public.sales_conversation(id);

CREATE INDEX idx_lead_conversation_id ON public.lead(conversation_id);

----------------------------------------------------------------------
2. Remove lead_id from sales_conversation (circular FK eliminated)
----------------------------------------------------------------------
ALTER TABLE public.sales_conversation DROP COLUMN IF EXISTS lead_id;

DROP INDEX IF EXISTS public.sales_conversation_lead_id_index;

----------------------------------------------------------------------
3. Backfill conversation_id for existing lead rows
----------------------------------------------------------------------
-- Only useful if lead_id still exists at the time of migration.
-- Run BEFORE step 2.
UPDATE public.lead l
SET    conversation_id = sc.id
FROM   public.sales_conversation sc
WHERE  sc.lead_id = l.id
  AND  l.conversation_id IS NULL;

----------------------------------------------------------------------
Environment variable required (no DDL change)
----------------------------------------------------------------------
The sales agent now uses shared Evolution host credentials from .env.
Add to .env:

    EVOLUTION_API_URL=<shared Evolution API base URL>
    EVOLUTION_API_KEY=<shared Evolution API key>
    EVOLUTION_WEBHOOK_SECRET=<shared webhook secret>

Only the per-agent instance name is stored in whatsapp_connection.
Twilio remains available only as deprecated rollback support.

----------------------------------------------------------------------
6. Keep only per-agent Evolution connection fields in whatsapp_connection
----------------------------------------------------------------------
-- Evolution is now the default provider. Shared host credentials live in .env.

ALTER TABLE public.whatsapp_connection
    ADD COLUMN IF NOT EXISTS provider VARCHAR(20) NOT NULL DEFAULT 'evolution',
    ADD COLUMN IF NOT EXISTS evolution_instance_name VARCHAR(255);

ALTER TABLE public.whatsapp_connection
    DROP COLUMN IF EXISTS evolution_api_url,
    DROP COLUMN IF EXISTS evolution_api_key_encrypted,
    DROP COLUMN IF EXISTS evolution_webhook_secret_encrypted;

CREATE INDEX IF NOT EXISTS idx_whatsapp_connection_provider
    ON public.whatsapp_connection(provider);

CREATE INDEX IF NOT EXISTS idx_whatsapp_connection_evolution_instance_name
    ON public.whatsapp_connection(evolution_instance_name);

----------------------------------------------------------------------
Why these changes exist
----------------------------------------------------------------------
A SalesConversation owns MULTIPLE leads — one per "purchase cycle".
The relationship is now a simple one-way FK: lead.conversation_id → sales_conversation.id.
The old circular dependency (sales_conversation.lead_id ↔ lead.conversations) is gone.
The "current lead" for a conversation is always the most recently created lead
with that conversation_id (ORDER BY id DESC LIMIT 1).

----------------------------------------------------------------------
4. New ConversationState value: awaiting_payment_method
----------------------------------------------------------------------
The sales_conversation.current_state column is VARCHAR(50) — no DDL change
is required. The ORM enum in app/models/conversation.py and the Pydantic
enum in app/schemas/pipeline.py both now include:

    AWAITING_PAYMENT_METHOD = "awaiting_payment_method"

This state is entered when both QR and physical payment methods are enabled
for an agent instance and the customer has completed checkout data collection.
The agent asks the customer which payment method they prefer before proceeding.

Existing rows are unaffected; the value will only appear in new conversations.

----------------------------------------------------------------------
5. New cart_contents fields written during payment flows
----------------------------------------------------------------------
The sales_conversation.cart_contents JSONB column gains two new keys
(no schema change needed, JSONB is schemaless):

  • "payment_method": "qr" | "physical"
      Set when the customer picks a payment method (or on direct physical
      flow). Read by the Telegram webhook callback to determine approval
      message text and post-rejection state.

  • "payment_proof_submitted": true
      Already existed for QR flow. Also set immediately for the physical
      flow (no actual proof is sent; the flag prevents the AWAITING_RECEIPT
      gate from asking the customer to re-send a receipt).
